# 設計上の決定

[English](DESIGN.md) | 日本語

これまでに決めたことと、その理由を記録する。各決定には却下した案も書き、同じ議論を繰り返さないようにする。決定には番号を付け、番号は振り直さない。覆した決定は削除せず、置き換えられたと記す。

用語は [GLOSSARY.ja.md](../GLOSSARY.ja.md) に従う。

## 問題

Spec driven development は、自然言語の文書を正として AI エージェントに実装させる。正が文書とコードの2つあり、必ずずれる。自然言語の文書は実行もテストもできないので、間違っていても誰も気づかない。文書の保守は、何にも強制されないコストになる。

Nindub は文書をなくす。正として残るものは実行可能でなければならず、そうすればずれは機械的に検出できる。

## 決定

### D1. Map が Terrain に先行する

Map を先に、人間が AI とともに書く。Terrain は AI が Map から生成する。Map が唯一の正である。

**却下:** 既存のコードから圧縮した「ミニチュア」を作ること。コードから作ったものは「今こうなっている」しか語れず、「本来どうあるべきか」を持てない。バグも忠実に写す。さらに、情報を落とせば正ではなくなり、落とさなければコードと同じ大きさになる。

### D2. Map は文書ではなくプログラムである

Map は超高級言語 Nindub で書く。Terrain がなくても単体で実行でき、テストできる。これが Map を正にする。Terrain が Map と食い違えば、テストが落ちる。

**却下:** 構造化されているが実行できない記述(スキーマと散文、図)。実行できないものは Terrain と照合できない。

### D3. Map はプロジェクト全体を書く。ドメインの中核だけではない

Map は、プロジェクトの観測できるものすべてを書く。状態、操作、画面、副作用、外部依存。

**却下:** Map をドメインロジック(状態・操作・不変条件)に限定し、UI・副作用・外部連携は従来の方法で作ること。観測できるのは戻り値だけだと思っていたときに検討した。中核に絞ると Nindub は型のついたドメイン層になり、既存の手法と区別がつかない。価値は全体を書けることにある。残りをどう観測可能にするかは D6 で示す。

### D4. 1ファイル、ズームできる

1つのプロジェクトは1つの Map ファイルである。Map の各要素は、Nindub でさらに分解されるか、Terrain で実現される。Zoom は、要素からそれを実現する Terrain の位置へ Pin をたどる操作で、Scale はその深さである。ファイルは入れ子構造を持つ1つの文書であり、平坦な一覧ではない。

*D17 により修正:Pin は Map ファイルには書かない。*

### D5. Map に何を書くかは Surface rule が決める

観測できる振る舞いは Map に書く。観測できないものは Terrain の裁量とする。データ構造、DB の選択、ライブラリ、フレームワーク、最適化。

UI にも同じ線を引く。各画面に何が表示され、ユーザーが操作すると何が起きるかは観測できるので Map に書く。色、レイアウト、フォント、アニメーション、UI フレームワークは Terrain の裁量であり、これは DB の選択と同じ扱いである。見た目は人間が目で判断し、振る舞いは Survey が判断する。

### D6. Survey は観測を比べる。状態は比べない

Survey は同じ入力列を Map と Terrain に流し、出てきたものを比べる。Terrain の内部状態は決して見ない。観測する経路は4つ。

| 経路 | 比べるもの | 先例 |
|---|---|---|
| 結果 | action と query の戻り値、宣言されたエラー | model-based testing |
| View | 各画面の構造をデータとして。何が表示され、何が操作できるか。ピクセルは見ない | Elm の view、ブラウザのアクセシビリティツリー |
| Effect | 副作用を実行せず、データとして出力したもの(このメールを送る、このカードに課金する) | effects as data、アウトボックスパターン |
| Port | 外部サービスへのリクエスト。型とエラーを宣言する | ports and adapters |

これを可能にするため、Map は各経路に対応する第一級の構文を持つ。`action`、`query`、`view`、`effect`、`port`。それに `state`、型、不変条件が加わる。

**却下:** Terrain の状態と Map の状態を比べること。Terrain の内部を知る関数が必要になり、D7 の問題を生む。

### D7. Projection は機械的である

Projection は、Survey が Terrain を駆動し観測するためのアダプタである。Map の宣言(action・query・view・effect・port のシグネチャ)と、Pin が指定するトランスポート(関数呼び出し、HTTP、ブラウザ)から生成する。人間も AI も手で書かない。

**却下:** Terrain の状態を Map の状態に写す関数を、人間または AI が書くこと。AI が Projection を書けるなら、AI は「Survey が通る Projection」を書ける。エージェントがテストを書き換えてテストを通すのと同じ穴である。状態ではなく観測を比べる(D6)ことで、手書きの Projection は不要になる。

### D8. 非決定性は注入する。Map の中には置かない

新しい識別子、時刻、乱数、外部サービスの応答は、Survey ハーネスが Map と Terrain の両方に与える入力である。Map の中に `now` や `random` のような環境依存の値はない。両側に同じシードと時刻を与えれば、比較は決定的になる。

### D9. すべての状態は観測可能でなければならない

Map のすべての `state` は、何らかの query または view から到達できなければならない。どの観測からも到達できない状態は、Surface rule により Map が扱うべきものではなく、Nindub のリンタが拒否する。

### D10. エラーは宣言し、種類で比べる

失敗は Map で型として宣言する(`requires ... else Forbidden`)。Survey は失敗したかどうかではなく、どの失敗が起きたかを比べる。

### D11. Terrain の構造に制約がかかる。これを受け入れる

D6 から D8 により、Terrain は Map のインターフェースを公開し、副作用をハーネスが横取りできる境界に通し、view を構造データとして取り出せるようにし、時刻と ID の供給源を外から受け取る必要がある。AI がゼロから Terrain を生成するならすべて満たせる。制約があることで、生成される Terrain の設計は揃う。

その結果も受け入れる。Nindub の対象は、Terrain を生成する新規プロジェクトである。既存のコードベースに Map を後付けすることは目標にしない。

### D12. Survey は探索であり、証明ではない

Survey は model-based testing である。入力列を生成し、Drift を探す。通ったということは、探した範囲で Drift が見つからなかったということであり、存在しないということではない。Map の型と不変条件により、探索の質は素朴なランダムテストよりはるかに高いが、主張は正直に述べる。

### D13. 人間は振る舞いを知るために Terrain を読まない

振る舞いは Survey の仕事である。性能、セキュリティ、運用性、見た目は Survey では観測できず、人間の責任として残る。主張は「何をするかを知るために Terrain を読む必要はない」であり、「Terrain を見なくてよい」ではない。

### D14. 名前、標語、避ける言葉

言語名は **Nindub**。ラガシュの王グデアの夢(グデアの円筒碑文、紀元前2125年頃)で神殿の平面図を描いた、シュメールの建築の神にちなむ。グデアは図に従って建て、ニンドゥブが図を描いた。開発手法は **Nindub Driven Development**。標語はボードリヤールの「地図が領土に先行する」。語彙は用語集で固定し、「spec」「model」「blueprint」は避ける。

**却下:** Gudea(描いた側ではなく建てた側)、Nawabari(活発に開発中のツールと同名)、Sashizu、Hinagata、Groma(それぞれ既に使われているか一般語)。

### D15. プロジェクトの取り決め

- オープンソース。ライセンスは MIT OR Apache-2.0。
- すべての文書は英語(`NAME.md`)と日本語(`NAME.ja.md`)で書き、同じコミットで揃える。
- Map の拡張子は `.nindub`(`.gd` は GDScript が使っている)。

### D16. 構文は Rust 風にする

Nindub は Rust の見た目を借りる。`struct`、`enum`、`Result<T, E>`、`match`、`let ... else`、クロージャ。トップレベルの語彙は Nindub 独自のもの(`state`、`action`、`query`、`view`、`effect`、`port`、`inject`、`invariant`)。最初の例は `examples/todo.nindub`、構文の説明は `docs/LANGUAGE.md`。

**却下:** TypeScript 風(緩すぎる。エラーと不在が第一級でない)、Elm 風(多くの読者と AI に馴染みがない)、独自構文(新しい構文に使う時間はインタプリタに使えない時間であり、AI は Rust をよく読める)。最初の草案では Pin を `#[pin(...)]` 属性として Map に書いたが、D17 で外した。

### D17. Map が変わるのは、人間が Amendment を採用したときだけ

Terrain が変わったことを理由に Map が変わることはない。Map が変わる理由はただ一つ、人間が Amendment(D18)を採用したときである。Terrain の整理、ファイル名の変更、フレームワークや DB の変更は、いずれも Map に触れない。

したがって Pin は Map には書かない。Pin は Terrain 側の注釈であり、実現している Map の要素と、観測するトランスポートを名指しする。Nindub のツールが Pin を集めて索引を生成し、Map の隣にコミットする。Zoom とビューアは索引を使い、ビューアは Pin を Map に重ねて表示してよい。Map ファイル自身は、ファイル、ルート、フレームワークを決して書かない。

**却下:** Map の中の属性としての Pin(`#[pin(ts = "src/api/todos.ts::create", via = http("POST /todos"))]`)。読みやすく Zoom も簡単になるが、Map が Terrain のファイル構成に依存する。ファイル構成は D5 により Terrain の裁量であり、Terrain を整理するたびに Map の編集が必要になる。これは正の向きを逆転させる。

### D18. AI は Amendment を提案し、人間が決める

Realize の途中で、AI は Map が間違っている(不変条件が成り立たない)、足りない(エラーの場合分けがない、port が要る)、沈黙している(ページングや重複について何も言っていない)ことに気づく。AI は決して Map を編集しない。Amendment を提出する。Map への diff、理由、そして現在の Terrain を改訂前の Map に対して Survey した結果を添え、その Amendment が許すことになる振る舞いを具体的にする。

人間は 3 つの判断のいずれかを下す。

| 判断 | 意味 | 効果 |
|---|---|---|
| 採用 | Map が間違っていた、または足りなかった | Map が変わる。Survey は新しい Map で回る |
| 却下 | Map が正しい | Terrain を直す。Survey は元の Map で回る |
| 裁量 | Map は沈黙しており、そのままでよい | 何も変わらない。その点は観測しないと記録する |

Amendment を起こすのは Drift だけである。Survey が検出しない Terrain の変更は、定義により Terrain の裁量の範囲内であり、レビューは要らない。

この経路は、D7 が Projection について閉じた穴を、別の場所に開け直す。AI が Survey が通るまで Map を弱める Amendment を提案しうる。エージェントがテストを消してテストスイートを通すのと同じである。Projection と違い、この穴は機械的には閉じられない。Map の変更が正しいかどうかは、人間の意図についての問いだからである。したがって人間の採用は便宜ではなく唯一の守りであり、添付する Survey 結果はそのレビューを具体的にするためにある。レビューの対象が短く高級な Map の diff であって Terrain の diff でないのも(D13)、同じ理由による。

### D19. ツールは TypeScript で書く

パーサ、インタプリタ、Survey ハーネスは TypeScript で書き、Node の型除去でビルドなしに直接実行する。実行時依存はない。

理由:一周が動くまでが最短であること(それがこのプロジェクトの最大のリスク)。Playwright が同じエコシステムにあり、view の Projection の候補であるブラウザのアクセシビリティツリーをそのまま取れること。最初の Terrain も TypeScript なので HTTP アダプタが同じ言語になること。AI が TypeScript を確実に読み書きできること。

**却下:** Rust。表面の構文と揃い、単一バイナリで配布できるが、どちらもインタプリタが早く存在することには寄与せず、ブラウザ操作は別プロセスになる。性能や配布が問題になる頃にはインタプリタの意味論がテストで固定されているので、書き直しは安全である。

## 注目すべき帰結

- Map の action・query・view が、そのままプロジェクトの公開インターフェースになる。別に API 定義を書く必要はなく、Map から導かれる。
- Map は Terrain なしで動くので、構造のプロトタイプでもある。実装が一切ない段階で、画面と操作を試せる。
- プロジェクト全体が1つの Map なので、Map を読んだ AI エージェントはプロジェクトを読んだことになる。最初の「ミニチュア」の発想が、逆方向から回収される。

## 未解決の問題

- **構文。** Rust 風(D16)で、`examples/todo.nindub` に草案がある。特に view の語彙は、何かが描画するようになれば変わる。
- **規模。** Todo アプリは1つの Map に収まる。認証つきのマルチテナントアプリが収まるかは分からず、それが D3 と D4 の本当の試験になる。
- **Terrain 側の view の観測。** ブラウザ UI については、アクセシビリティツリーが機械的な Projection の候補である。比較に耐える安定性があるかは未検証。
- **並行性。** イベントと注入された時刻で非同期は原理的に扱えるが、インターリーブは考え切れていない。
- **Map の変更。** 状態の形が変わると、Terrain が保存しているデータの移行が必要になる。誰が移行を書き、Survey がどう検証するかは未定。
- **Survey の網羅性。** 不変条件を使って入力生成を誘導する方法と、何を探索したかを報告する方法。
