### 確かめ方

次の Map を `node src/cli.ts run` で実行すると、H10、H11、H12、H13、H14、H15 を再現できる(`:port Ext.hit Ok(1)` を先に入力する)。

```rust
map Probe;
struct Row { id: Text, n: Int }
enum Error { Bad }
effect Ping { n: Int }
effect Pong { n: Int }
port Ext { fn hit(n: Int) -> Result<Int, Error>; }
state rows: Table<Row>;
invariant "n is never 5" { rows.all(|r| r.n != 5) }
query sneaky(k: Text) -> Int {           // H10: query が状態を変え、effect と port を出す
    rows.insert(Row { id: k, n: 1 });
    emit Ping { n: 1 };
    let r = Ext.hit(1) else Error::Bad;
    r
}
view Screen(k: Text) { heading("n=" + sneaky(k)); }                         // view の描画でも起きる
action put(k: Text, n: Int) -> Result<(), Error> { rows.insert(Row { id: k, n }); Ok(()) }  // H11: 同じ k で上書き
action step(k: Text) -> Result<(), Error> { put(k, 5); rows[k].n = 6; Ok(()) }            // H12: 途中で違反と報告される
action fail(k: Text) -> Result<(), Error> { let r = Ext.hit(9) else Error::Bad; requires false else Error::Bad; Ok(()) } // H13: port リクエストが残る
action pp() -> Result<(), Error> { emit Ping { n: 1 }; emit Pong { n: 1 }; Ok(()) }       // H15: 2つが同じ JSON になる
action txt() -> Result<Text, Error> { Ok("Error::Bad") }                                   // H15: 次と同じ JSON になる
action en() -> Result<Error, Error> { Ok(Error::Bad) }
```

`put("z", "not an int")` も成功する(H14)。

## 第2部:改善案

### P1. 言語の意味を文書で確定し、版を付ける

- **意味の正を文書にする。** `docs/SEMANTICS.md`(英日)を言語の意味の正とし、インタプリタをその実装と位置づける。文書の各項目には、それを確かめる例をテストとして付ける。
- **H11 への答え:** `insert` で既存の id を指定したら、Map の誤りとする(下の「Map の誤り」)。上書きしたい場合は別の操作(`upsert` など)で明示する。
- **H12 への答え:** invariant は、**最も外側の action の終わり**で検査する。入れ子の action は、1つの取引の一部として扱う。
- **H13 への答え:**
  - 失敗した action の port リクエストは取り消せないので、送ったものとして Observation に残す。これを文書に明記する。
  - Map の実行時エラー(応答がない、行がない、`match` の腕が足りない、計算の上限を超えた)は、例外ではなく **「Map の誤り」という結果**として Observation に入れる。Survey は Map の誤りを Terrain と比べず、Map のバグとして報告する。止まらない再帰には計算の上限を設け、超えたら Map の誤りとする。
- **H16 への答え:** Id と Text は、Table の鍵でも `==` でも区別する。REPL で文字列から Id を作るときは、引数の型(P2)に従って変換する。
- **H17 への答え:**
  - Int は 64 ビットの符号付き整数とし、あふれたら Map の誤りとする。除算は 0 に向かって切り捨てる。
  - Text の長さはコードポイントで数え、順序もコードポイント順とする(UTF-16 順ではない)。
  - Instant は UTC のミリ秒とし、Text に変換すると ISO 8601 の形式になる。
- **H19 への答え:** invariant は、Map 側の自己検査と、Survey の入力生成の手がかりと定義する。LANGUAGE の「Terrain では query を通して」は削る。観測が一致していれば、Map 側の検査で足りる。
- **H20 への答え:** `state name: Type = 式;` で初期値を書けるようにする。式は定数に限る。
- **H18 への答え:** Map の先頭で言語の版を宣言する(例:`map Todo; nindub 0.1;`)。意味が変わるインタプリタの変更は、版を上げて行う。Map の版を上げることは Amendment として扱い、Remap で適用する。そのとき P10 の「Map と Map の Survey」を、旧い版と新しい版の間で回して添付する。これで D17 の「Map は Remap でのみ変わる」が、テキストだけでなく意味についても成り立つ。
- **塞ぐ穴:** H11, H12, H13, H16, H17, H18, H19, H20
- **既存の決定への影響:** LANGUAGE の「知っておくべき意味」を SEMANTICS に移して広げる。D17 と D19 に「意味の版」を補う。

### P2. 型を検査する

- Survey の前に静的な型検査を行う。検査するものは次のとおり。
  - フィールドと引数の型
  - `Id<T>` の `T` の区別
  - `match` の網羅性
  - action と query が返しうるエラー(`Result<T, E>` の `E` の中で、実際に `requires` や `let ... else` から出てくる種類)の一覧
- D9(すべての状態が観測できる)の検査も、ここで実装する。
- Survey の入力生成は、この型に従う。
- **塞ぐ穴:** H14。H35 の一部(存在しないリンタ)。
- **既存の決定への影響:** なし。D9 と D16 を実装するだけである。

### P3. 読み取りの純粋さを言語で保証する

- query と view の中では、次を型検査(P2)で禁止する。
  - `state` への代入、`insert`、`remove`
  - `emit`
  - `query` の印のない port 関数の呼び出し(印は P5 で導入する)
- これで LANGUAGE の「view の描画は状態を変えず、effect を出さない」が本当になる。Survey は view を何度描画しても、世界に影響を与えない。
- invariant を action の後だけで検査すれば足りることも、この保証から従う。
- **塞ぐ穴:** H10。H35 の一部。
- **既存の決定への影響:** Query の定義(状態を変えずに読む)を強制するだけである。

### P4. Observation の正準形と、トランスポートの規約

- **正準形を1つ決める。** Observation の表現を、情報を落とさない1つの形に決める。Map 側でも、Projection を通した Terrain 側でも、同じ形で比べる。
  - struct と effect は型名を持つ
  - enum は Text と区別できる形にする
  - Id は Text と区別する
  - Int は常に10進の文字列にする
  - `form` の送信先は、action の呼び出しの型として表す(例:`create(user, $title)`。`$title` は入力欄)
- **`.then` の意味を決める。** action が `Ok` を返したときだけ遷移する。
- **HTTP の規約:** 引数、Result、エラーをどう載せるかを、Nindub が1つだけ定める。Pin で選べるのはメソッドとパスだけにする。
- **ブラウザの規約:** view の要素をアクセシビリティツリー上の部品に対応させる規約を定める。
  - `heading` は見出し、`button` はそのラベルを名前に持つボタン、`item` はリストの項目
  - `form` の入力欄は引数名をラベルにする
  - ラベルは正確に比べる
- これで Projection は、シグネチャと規約だけから完全に機械的に作れる。
- **塞ぐ穴:** H15, H21, H22
- **既存の決定への影響:** D6(view の観測の中身)と D7(Projection の材料)を具体化する。どちらも変更ではない。

### P5. 注入の意味を整理し、「外部世界」を導入する

- **時刻:** 1回の入力の処理中は、`clock.now()` を何度読んでも同じ値を返す。インタプリタの既定の時計もそう改める。
- **ID:** 注入はこれまでどおり行う(D8 を維持する)。ただし比較は「ID の一貫した付け替えを除いて一致するか」で行う。Terrain が ID を何回取っても Drift にならない。
- **外部世界:** Survey は、実行1回ごとに一貫した「外部世界」を与える。同じリクエストには同じ応答が返る。同じ外部世界を、REPL や単体実行の port の応答にも使う(ファイルに書いておける、引数ごとに応答を変えられる)。外部世界は、各 port のエラーの種類を必ず一度は返す(P12)。
- **port の `query` 印:** port の関数に `query`(外部を変えない読み取り)の印を付けられるようにする。`query` の印のある port へのリクエストは比べず、結果への影響だけを比べる。印のないリクエストは、これまでどおり列として比べる。
- これで、キャッシュ、バッチ化、読み取りのリトライは Terrain の裁量に戻る。
- **塞ぐ穴:** H7, H8, H24
- **既存の決定への影響:** D6 の表の Port の行を改める(「リクエストを観測」を「`query` 以外のリクエストを観測」に)。D8 を補う。

### P6. 許容幅を Map に書けるようにする(裁量の記録場所)

- Map は決定的で実行できるままにする(D2 を維持)。そのうえで「この点はこの範囲で違ってよい」という比較の許容幅を宣言できるようにする。例:
  - `query list` の結果は、順序を問わない。あるいは、同じ時刻どうしの順序は問わない。
  - 複数の `requires` に同時に違反したとき、どちらのエラーを返してもよい。
  - `text()` に埋め込まれた日時や数値の書式は問わない(値だけを比べる)。
- インタプリタは、許容幅の中の1つの振る舞い(P1 で決めたもの)で動く。
- D18 の「裁量」判断は、**許容幅を加える Amendment** として Map に記録する。これで「Map は Remap でのみ変わる」(D17)が保たれ、正は Map 1つのままである。
- **塞ぐ穴:** H9
- **既存の決定への影響:** D18 の表の「裁量」の効果を「何も変わらない」から「許容幅を加える Remap」に改める。GLOSSARY に新しい用語を英日で加える。

### P7. 閉じた表面:Terrain の出入口は Pin と宣言だけにする

- **入口:** Pin の索引から、本番の入口(ルーターやゲートウェイ)をツールが生成する。Pin のない経路には外から届かない。Survey が叩く経路が、本番の唯一の経路になる。
- **Pin の網羅:** Map の action、query、view には、トランスポートごとにちょうど1つの Pin がなければならない。欠けても重複してもエラーにする。この検査は Pin の索引を作り直すたびに行い、Remap の後にも行う(P10)。
- **出口:** Survey 中の Terrain は、宣言された port 以外への通信を禁止する。本番でも、port の宣言から許可リストを生成することを推奨する。effect を実際に行う部分(メールの送信など)は effect の境界の外側に置き、Survey 中はハーネスが受け取る。
- **初期化:** Terrain は Survey のために「空の状態に戻す」口を持たなければならない。これを D11 の制約に加える(H23)。
- **塞ぐ穴:** H1, H2, H3, H23
- **既存の決定への影響:** D18 の「Survey が検出しない変更は裁量」を「**閉じた表面の内側で** Survey が検出しない変更は裁量」に改める。D11 に項目を加える。

### P8. 本番での Survey

- P7 の入口と出口で、本番の入力、注入値、観測を記録し、Map に流して答え合わせをする。
- Survey と本番では同じビルドを使うことを義務づける。違うのは注入の中身だけにし、Survey 中かどうかを判別するコードはリンタで禁止する。
- 記録には利用者のデータが含まれる。保存場所と保存期間は、プロジェクトごとに人間が決める。
- **塞ぐ穴:** H4。H31 の補強(実際の利用で通る経路が探索に加わる)。
- **既存の決定への影響:** なし。D12(探索であって証明ではない)はそのまま成り立つ。

### P9. 行為者を引数から分ける

- 行為者を引数とは別の文脈として書く。例:`action complete(id: TodoId) by user: UserId`
- Projection は、行為者を P4 のトランスポート規約にある認証の欄(cookie やトークン)で運ぶ。引数としては運ばない。
- Survey は、別人を名乗る入力も生成する。
- 認証の方式は Terrain の裁量とし、「誰が何をできるか」だけを Map に書く。
- **塞ぐ穴:** H29
- **既存の決定への影響:** LANGUAGE の「未設計:セッションと認証」に方向を与える。

### P10. Amendment と Remap の経路を整える

- **起点を2つにする。** 人間が起こす Amendment(機能の追加や変更)と、AI が Realize の途中で起こす Amendment である。どちらも同じ審査を通り、採用されたら Remap される。AI が起こす場合は、Drift か、問題を示す具体的な入力列を必ず添える。「沈黙」の指摘も、入力列で示す。
- **最初の Map は、空の Map に対する Amendment の列として作る。** 最初の Map も同じ審査を通る。
- **Map と Map の Survey を添付する。** 改訂前と改訂後の Map はどちらも実行できるので、観測が変わる入力列をツールが探して添付する。許容幅を広げる変更(P6)には、弱める方向の変更だと目立つ印を付ける。
- **下書きは中立に示す。** ツールが Drift から Amendment の下書きを作る場合(D17)、同じ入力列に対する Map の観測と Terrain の観測を並べて示す。下書きには「Terrain の振る舞いから作った」と明記し、理由の欄は人間か、下書きとは別に AI が埋める。採用と却下のどちらも既定にしない。
- **ベースの版を記録する。** 各 Amendment は、どの版の Map に対するものかを記録する。Remap できるのは、ベースが今の Map と同じ場合だけとする。違えば、今の Map の上に取り込み直し、Survey と Map と Map の Survey を回し直す。
- **Pin の検査:** Remap の後、ツールは Pin の索引を作り直し、P7 の網羅検査を行う。消えた要素や名前が変わった要素を指す Pin は、Terrain 側の修正として報告する。Map は変えない。
- **理由を残す。** 採用された Amendment の理由は、履歴として保存する。この履歴は自然言語で書かれるが、正ではない。「なぜ」を知るための記録である。
- **塞ぐ穴:** H5, H6, H25, H26, H27, H28, H34
- **既存の決定への影響:**
  - D18 の「Amendment を起こすのは Drift だけ」を「AI が起こす Amendment は証拠を伴う」に改める。
  - GLOSSARY の Amendment の定義を、2つの起点を含むように広げる。
  - D17 の下書きに、中立に示すという条件を加える。
  - D17 と Remap の定義そのものは変えない。

### P11. 移行を検証する Survey

- 状態の形を変える Amendment は、Nindub で書いた移行関数(改訂前の Map の状態から、改訂後の状態へ)を必ず含む。
- Survey は次の手順で移行を確かめる。
  1. 入力列の前半を、改訂前の Map と改訂前の Terrain に流す。
  2. 両方で移行する(Terrain 側の移行は AI が書く)。
  3. 入力列の後半を、改訂後の Map と改訂後の Terrain に流し、観測を比べる。
- 状態そのものは比べないので、D6 に反しない。
- **塞ぐ穴:** H30

### P12. Map の上で網羅率を報告する

- Survey は、次のものを通ったかどうかを Map の上で報告する。
  - 各 `requires` とその `else`、`match` の各腕
  - view の各操作
  - 各 effect
  - port の各エラーの種類(P5 の外部世界が必ず返す)
  - Map の誤り(P1)
- 「通った」とは「この網羅率で Drift がなかった」という意味だと明示する。
- **塞ぐ穴:** H31
- **既存の決定への影響:** D12 の正直な主張を数字で裏づける。

### P13. 定義と文書を揃える

- 「観測できる」を「4つの観測経路で観測できる」と閉じた形で定義する。速さ、資源の使用量、見た目は、D13 の人間の責任だと明記する(H32)。
- Scale を定義し直す。1ファイルの中では、上の階層はシグネチャと invariant、下の階層は本体とする。Map の外に降りるには Pin を使う(H33)。
- LANGUAGE の冒頭の状態表示、D9 のリンタの記述、view の描画についての記述を、実装と P1〜P3 に合わせて改める(H35)。
- **塞ぐ穴:** H32, H33, H35

## 第4部:これらの案を採っても残る穴

- **並行性:** 同時に届く入力のインターリーブ(既知)。P5 の時刻の固定は、1回の入力の中の話にとどまる。
- **規模:** 大きなアプリの Map が1ファイルに収まるか(既知)。P13 の Scale の整理は読みやすさを助けるが、答えにはならない。
- **多言語対応:** ラベルを正確に比べる(P4)限り、翻訳はできない。許容幅をラベルに広げると、UI の部品を特定する目印を Terrain 側に置く必要が出て、H1 に似た穴が開く。
- **Map の内容が意図どおりかどうか:** 完了済みの todo でメールがもう一度送られる件のように、Map が正しく動いていても、それが人間の意図と合っているかは機械では決められない。P10 は審査の材料を具体的にするだけである。
- **速さ、セキュリティの実装、見た目:** これまでどおり人間の責任である(D13)。
- **実装の言語が同じであること:** インタプリタと最初の Terrain はどちらも TypeScript である(D19)。同じ言語の癖(たとえば文字列の比較順)が両側に同じように入り込み、Drift が隠れるおそれがある。P1 で意味を文書に固定し、例によるテストで確かめることで小さくはできるが、なくすには別の言語で書いた Terrain で試す必要がある(ロードマップの 5)。
